# Arcade Gambit

Arcade Gambit is a responsive, 16-bit Amiga/demoscene-inspired chess game built with React, TypeScript, Vite, and `chess.js`. Choose an unlocked boss from the 100–3000 Elo ladder (50-point steps), then play on a separate battle screen.

## Run locally

```sh
npm install
npm run dev
```

Create a `.env.local` from `.env.example` to enable Supabase sign-in and cloud progress. Without it, the app works in guest mode and stores progress in this browser's local storage.

## Supabase setup

1. Set separate development and production URLs and publishable keys in `.env.local`, using the four variables in `.env.example`. Localhost, `.localhost`, `.local`, loopback, and private LAN IP addresses use `VITE_SUPABASE_DEV_URL` and `VITE_SUPABASE_DEV_PUBLISHABLE_KEY`. Public domains, including `https://arcadegambit.com` and `www.arcadegambit.com`, use `VITE_SUPABASE_PROD_URL` and `VITE_SUPABASE_PROD_PUBLISHABLE_KEY`. Selection uses the browser hostname, including when previewing a production build locally. Missing development settings keep localhost in guest mode; it never falls back to production. Development and production cannot point at the same Supabase origin. Legacy `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`/`VITE_SUPABASE_ANON_KEY` are accepted only for production. Restart Vite after changing environment files; set the same variables in your hosting build environment and rebuild when deploying.
2. Run [`supabase/schema.sql`](supabase/schema.sql) in each environment's Supabase SQL editor. It creates row-level security, idempotent atomic progress RPCs, the account game archive and save RPC, and migrates existing progression. Re-run it when upgrading an existing Supabase project.

   Account deletion requires running [`supabase/account-deletion.sql`](supabase/account-deletion.sql) after `schema.sql` and `multiplayer.sql` in each environment before deploying the frontend. Profile → **Delete my account** shows an irreversible-data-loss warning and a final “Are you really sure?” dialog. The authenticated `delete_own_account()` RPC deletes only its caller, atomically removing Auth data, progress, private archives, rating, queue and seats. Other players retain their chess records with the deleted participant's ID removed and name/PGN player header replaced with **Deleted user**. Live human games end as an unrated forfeit; practice games and games with no remaining human owner are removed. Local account caches and the session are cleared, and the app reloads in guest mode. The Auth deletion trigger also applies to administrator-initiated deletions. Run `node account-deletion-check.mjs` to verify deletion, anonymization, rollback, and access control.
3. Enable Google, GitHub, Facebook, and Email providers in Supabase Authentication. Configure each OAuth provider's client ID/secret in Supabase and register each project's `https://<project-ref>.supabase.co/auth/v1/callback` URL in the corresponding provider's developer console. The app supports email/password signup, login, and password recovery; email signup requires confirmation. New passwords require at least 8 characters and matching confirmation. Configure custom SMTP for confirmation and recovery emails to users outside the Supabase organization (the built-in mailer is restricted).
4. Allow localhost/LAN app redirect URLs only in development Supabase. Allow `https://arcadegambit.com` (and any supported public domains) in production Supabase. Configure OAuth providers separately for each environment.

The browser uses only the Supabase publishable/anon key. Never put a service-role key in a `VITE_` variable.

Signed-in games save every committed move to `player_games`, including full Standard or Chess960 PGN, opponent, player color, and result. History includes **Resume game** for every unfinished match and **Review** for all games. Local account caches retain offline saves; uploads retry on reconnect, focus, and every 15 seconds. History loads in pages so older games remain available. Guest history is claimed by the first account that signs in on that browser and then removed from the guest archive. Account histories are isolated by user ID, with RLS enforcing cloud access. Signed-in profile pictures use OAuth avatar metadata, with initials if no image is available.

The save RPC prevents stale positions with fewer moves from overwriting newer ones and preserves completed results. Simultaneous play of the same match on multiple devices is not a collaborative game session; continue a match on one device at a time.

### Human matches and online Elo

During human games, **Chat** and **Emojis** have their own tabs in the left panel. Match chat is available immediately to the two participants and stays scoped to that match. **Add friend** lets players continue a separate private conversation in the online lobby after both accept. Removing a friend clears their private lobby conversation; match chat stays with its game. Each conversation displays the latest 50 messages and accepts up to 500 characters per message. Tabs support keyboard navigation and preserve message drafts.

The **Emojis** tab offers 62 reactions, with chess pieces and chess-themed symbols first. **Emoji reactions enabled** switches them off immediately and saves the preference to the account (or the browser for guests). It is also available in Settings, but hidden before a game. Either human player's preference stops sending reactions between them. Reaction popups disappear after eight seconds, while their entries remain in the latest 50 messages of the match chat history; the server limits reactions to one every two seconds and chat to one message per second. Spectators cannot access communication. Social polling runs only in the online lobby, human match and result screens, pauses in hidden tabs and stops after a connection error until Retry. Home's request budget is unchanged.

Practice and ladder bots offer local chat with clearly labeled preset replies and the same 62 emoji buttons. Bots react to captures, checks, castling, promotions and the result. Reaction popups disappear after six seconds, while player and bot reaction entries remain in the local chat history, and are spaced at least eight seconds apart; a result can interrupt the cooldown. Quiet moves and repeated state polls do not trigger reactions. The emoji toggle hides both the buttons and reactions. Bot conversations last for the current game view, stay on the device, and make no server calls. Bot matches load a signed-in account's emoji preference once, without social polling. Run `node bot-reactions-check.mjs` and `node social-ui-check.mjs` to verify events, buttons, cooldown, expiry and mute persistence.

Apply `supabase/social.sql` **after** `supabase/multiplayer.sql` in development and production before releasing this frontend. The authenticated `online_social` RPC owns friendship consent, match participation, message validation and rate limits; clients have no direct access to social tables. Social rows are removed with their accounts. Verify with `node social-check.mjs` (the same temporary PGlite install used by multiplayer checks) and `node social-ui-check.mjs` (Playwright/Edge, mocked API, desktop and mobile).

All page containers use the full viewport width with small responsive gutters; square boards retain their viewport-height limits. On phones, the board appears above the communication panel. `node communication-layout-check.mjs` checks 2560/1440/1024/390/320px layouts, all main routes, tab switching, message drafts, incoming chat, escaping and overflow. `--live` checks the deployed frontend with mocked account requests.

Signed-in players have a **Play against human** button on the home page. Choose **3, 5, 10 or 15 minutes per player**, with no increment. Matchmaking pairs the closest available overall online Elo in the same time control, with random colors. Queue entries expire after 15 seconds without a heartbeat. If no opponent is available after 20 seconds, the server starts an explicitly labeled **unrated practice bot** game. Canceling a search is safe if a match has just been made: that match is returned instead of silently abandoned.

Human and fallback-bot battles use the ladder's board frame, piece artwork, drag-and-drop, board sizing, move highlights, theme selectors and sound effects. Board, piece and sound choices persist across both modes. Battle music uses the same track and independent mute/volume controls. Queue any number of premoves by clicking or dragging during the opponent's turn. The board previews your planned positions, including repeat moves with the same piece. Selection and dragging survive an opponent's move unless the selected piece is captured. Cancel the queue with its button, Escape, or right-click. On each turn, only the next move is checked and executed; an illegal move cancels it and the remaining queue. Promotion opens the piece chooser before committing. This also applies to Standard and Freestyle boss battles. Run `node premove-ui-check.mjs` to verify queues, selection, dragging, both colors, cancellations and previews. Legal player moves appear and sound immediately while the server saves them. A pending move cannot be sent twice; premoves can be queued during saving. Rejected or conflicting moves restore the confirmed position. A lost reply is reconciled through a state read instead of blindly resending. Clocks, results, and ratings remain server-owned.

The home-page **Play against human** card shows **Resume**, **Resign current game** (with confirmation), and the remaining seconds before auto-resign while away. Home uses a cached, read-only snapshot and never invokes the multiplayer Edge Function. The countdown runs locally; an expired countdown makes no request. Opening the game lets the server determine its result. Returning home does not keep an abandoned match alive. When a game finishes, its match URL displays a dedicated result screen with the winner, reason, rating change, clocks, captures, and both players' estimated accuracy. Result and review share the same analysis worker and a bounded in-memory cache of completed analyses. **Review game** opens replay; **New N-minute game** starts human matchmaking with the previous time control, retaining the 20-second practice-bot fallback.

The fallback practice bot waits an extra 1-5 seconds on each turn before choosing its move. The server derives a stable pseudorandom delay for each game and ply, so repeated polls or reconnects cannot skip or restart the wait. Its clock keeps running during thinking, and heartbeat requests return immediately.

The multiplayer Edge Function verifies the signed-in user with Supabase Auth, replays the stored PGN with `chess.js` and validates each move. PostgreSQL locks the game, checks the expected version, debits the active clock using server time, and commits the move or result. Browser clocks are displays only. State refreshes and heartbeats run every two seconds. Closing the browser sends a best-effort disconnect notification; abrupt kills or network failures are detected from the last heartbeat. Return within **20 seconds** to continue, otherwise the disconnected player forfeits (also in unrated bot practice). Neither clock pauses. The server checks expiry before accepting a returning player's heartbeat, and heartbeats do not change move versions. The earlier of clock expiry or the reconnect deadline decides the outcome; if both players' reconnect deadlines are identical, abandonment is a draw. Expiry is committed on the next server request for that game, including the return request if everyone was offline. Opponents see the remaining reconnect countdown. Automatic chess.js draw rules include stalemate, insufficient material, threefold repetition and the fifty-move rule. Human players can also offer/accept a draw or resign.

Every committed move is stored in `online_games`. Both participants can read their live game. Once completed, it appears in personal and community online history, with names, clock, result, PGN and rating changes visible to other signed-in players. **Analyze & replay** opens the existing review. Traditional boss-run archives keep their existing private access rules. Online games do not unlock ladder rungs or modify boss-run counters.

Each account starts with **1200 internal online Elo**, shared across the four clocks. Human results use the [FIDE rapid and blitz rating regulations](https://handbook.fide.com/chapter/B02RBRegulations2024), specifically table 7.1.2 and the rating-change formula: `K × (actual score − expected score)`. Rating differences are capped at 400; wins/draws/losses score 1/0.5/0. K is 40 for the first 30 rated games, then 20, or 10 after a player has reached 2400. Integer changes round halves away from zero. Both ratings and the completed game commit in one transaction; retries cannot award points twice. Bot practice, games without a move by both sides, and gaps of at least 600 when either player is above 2600 are unrated.

This is **FIDE-based internal Elo**, not an official FIDE rating: initial 1200 is an app seed, there is one shared pool, adult K rules apply without collecting birth dates, and each game is treated as its own rating period rather than a monthly federation submission. Three-minute games are supported as online games even though FIDE's cited over-the-board blitz definition requires more than three minutes. Official publication/initial-rating requirements, youth coefficients and monthly volume adjustments are not claimed here.

### Multiplayer request budget

After installing the roles backend below, apply `supabase/multiplayer-transport.sql` in development and production before releasing the current frontend. This adds authenticated `online_state`, `online_matchmake` and `online_disconnect` RPCs. They derive the caller from Auth, enforce account restrictions, and preserve live-game privacy. Clients still cannot directly call the service-only pairing/commit helpers or write clocks, PGNs, results or ratings.

The previous transport invoked the `multiplayer` Edge Function every two seconds per active player (1,800 state calls per player-hour), including fallback practice and matchmaking. Routine polling, presence, search/cancel, disconnect and completed review now use database RPCs and make **zero Edge invocations**. An Edge call is made for a player move, resign/draw action, a due bot decision, or clock/disconnect adjudication. Bot timing and expiry flags are computed by the database from saved server state; move legality, material-dependent timeout outcomes and Elo remain trusted server decisions. No Realtime subscription or additional Realtime message budget is introduced.

State polls still run every two seconds for prompt opponent updates and the existing 20-second reconnect window. When the version is unchanged, the server returns only timestamps/presence rather than the full PGN and match snapshot. Uncertain moves force a full read to reconcile a lost reply without resending. Completed matches stop state polling, permanent access/not-found errors stop automatic retries, transient errors back off up to ten seconds, and bursts of focus events share the polling interval. Chat/social/admin polling uses database RPCs, not Edge Functions; it still contributes to database traffic/egress. Google Analytics does not invoke Supabase functions.

## Administration and site statistics

Run [`supabase/administration.sql`](supabase/administration.sql) and then [`supabase/roles.sql`](supabase/roles.sql) after `schema.sql`, `multiplayer.sql` and `social.sql` in each environment. `roles.sql` replaces the earlier super-administrator model with exactly two roles: **User** (default) and **Administrator**. Every active administrator can search accounts by email or name, grant/remove other administrators, ban users, suspend them for 1 hour / 1 day / 7 days / 30 days, and restore access. The account dialog shows the role; administrators get an **Administration** home link (`#administration`; `#statistics` remains supported). Roles come from private database records, never user-editable metadata, names or email matches. The verified Google account `ekim197711@gmail.com` (Mike Møller Nielsen) was explicitly granted administrator access in development and production. New environments need an explicit trusted administrator bootstrap.

Moderation requires a reason and confirmation, records an audit event, and cannot target the caller's own account. Active matches end as unrated forfeits when an account is restricted. Supabase Auth's `banned_until` blocks further authentication; database policies, guarded save/social/game RPCs and the multiplayer Edge Function also enforce restrictions on existing sessions. Suspension expiry restores access automatically; bans continue until restored. The UI refreshes role/access status every 30 seconds and shows the reason and suspension end time to restricted accounts. Reapply `roles.sql` after replacing any game/schema RPC definitions, then deploy the multiplayer function in both environments. Direct access to administrator, restriction and audit tables is denied to browser clients.

Statistics show current registered non-anonymous accounts (including unconfirmed signups, excluding deleted accounts), unique signed-in users seen within 90 seconds, and completed games today (Europe/Copenhagen), in the last hour, 7 days and 30 days. Counts include saved Standard/Freestyle boss games, human matches counted once per match, and practice bots; debug games and device-only guest games are excluded. An idempotent trigger/backfill ledger keeps game totals after account deletion and prevents retries/repeated saves from double counting. Boss completion dates use the saved archive timestamp, capped at server time, including when offline history uploads later. Older deleted/unsaved games cannot be recovered by the backfill.

Presence is a deliberate exception to the data request budget below: one `app_heartbeat` RPC on sign-in and every 30 seconds while a tab is visible also returns the database-authorized role or restriction. Restricted accounts additionally read their own reason/end time. Visibility events are throttled to at most one attempt per 25 seconds; hidden tabs stop heartbeats. Tabs share one server presence row per account; after leaving, presence expires within 90 seconds. Statistics refresh every 30 seconds only while that page is visible. Presence never flushes pending games/progress or reloads home snapshots. Run `node roles-check.mjs` for the final roles/moderation security model, `node administration-check.mjs` for the underlying statistics migration and `node administration-ui-check.mjs` for access, moderation, role management, presence and responsive UI checks.

## Gambit Academy

Open **Train gambits** under **Gambit Academy**, directly after **Boss Run** in the home Play card (or visit `#gambits`). The academy bundles 471 gambit families and 1,315 named opening lines from the CC0 Lichess chess-openings catalogue. Search the catalogue, select a scenario, and follow the boss's square-by-square instructions. White and Black training are supported; switch sides explicitly with **Train the other side**. Optional spoken coaching uses the browser's speech synthesis.

Stockfish 19 runs locally in a worker. Guided lessons constrain its search to accepting replies. Setup-only and declined catalogue lines are extended or adapted to reach a legal acceptance, with a visible notice when the source line changes; **Play on against Stockfish** removes that constraint. Engine failures expose a retry action without changing the position. Off-line moves are rejected without changing the board and explained as variation mismatches, since an alternative legal move is not necessarily a chess mistake.

Each named line must be cleared before its family is marked mastered. This measures completion of the supplied opening repertoire, not chess strength. Clears are stored locally per account ID (or guest), independently of ladder progress, and are not cloud-synced. Some obscure gambits have only one named line in the source catalogue. The catalogue is comprehensive within that source, not a claim to enumerate every gambit ever invented.
